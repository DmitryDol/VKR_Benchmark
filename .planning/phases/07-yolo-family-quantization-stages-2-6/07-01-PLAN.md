<objective>
Close the two foundational gaps that block every later YOLO optimization stage:

1. **ONNX export (D-01, OPT-YOLO-01):** No code currently exports YOLO models via the
   `ultralytics` exporter. The CLI stage 1 path uses `PyTorchEngine` (which never
   produces ONNX), and stages 2-6 all expect `weights/{model}/{model}_sim.onnx` to
   already exist. `yolo11l_sim.onnx` is missing entirely and the existing
   `yolo26l_sim.onnx` has unknown provenance. Add `export_yolo_to_onnx()` to
   `onnx_export.py` and wire it into the Stage 2 CLI path so both YOLO ONNX files are
   produced deterministically from `.pt` weights.
2. **TensorRT engine filename collision (D-04):** `tensorrt_engine.py` hardcodes the
   `rtdetr_` prefix into every `.engine` and `.cache` filename. Building TRT engines
   for `yolo11l` and `yolo26l` would overwrite each other AND clobber the v1.0 RT-DETR
   engines in `engines/`. Re-key all engine/cache paths by `self.model_name`.

Purpose: Without these, Stages 3-6 cannot run for the YOLO family — they have no ONNX
input and would corrupt each other's TRT engine cache.
Output: `export_yolo_to_onnx()` function, two simplified YOLO ONNX files producible via
the CLI, model-name-keyed TRT engine paths, updated test coverage.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.pt` weights → ultralytics export → ONNX graph | YOLO weight files are deserialized by ultralytics (PyTorch `torch.load` under the hood) and traced into an ONNX graph. A tampered `.pt` could embed malicious pickled objects or a corrupt graph. |
| ONNX file → onnxsim → TensorRT parser | The simplified ONNX graph is the input to the TRT builder in later plans; a malformed graph could crash the builder or produce an invalid engine. |
| CLI args (`--model`, `--engine-dir`, `--output-dir`) → filesystem paths | User-supplied paths feed `engine_dir` / `output_dir` and the derived engine/cache filenames. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | YOLO `.pt` weights loaded by ultralytics in export_yolo_to_onnx | accept | Local single-user academic tool; weights are operator-provided files from the official ultralytics distribution, not network input. No untrusted upload path exists. Documented as accepted per the phase security note (ASVS L1, proportionate). |
| T-07-02 | Tampering | ONNX graph integrity after export+simplify | mitigate | `export_yolo_to_onnx()` calls the existing `validate_onnx()` (`onnx.checker.check_model`) on the final simplified file before it is handed to any downstream stage; onnxsim's own check result is logged on failure. |
| T-07-03 | Tampering | Engine/cache filename derived from `model_name` | mitigate | `model_name` is sanitized to alphanumeric/dash/underscore via the `model_token` regex sub before being interpolated into a filename, preventing `../` traversal or separator injection into `engine_dir`. `engine_dir` itself is already `.resolve()`-d in cli.py (T-03-06). |
| T-07-04 | Denial of Service | Malformed ONNX crashing the TRT builder (later plans) | accept | Build failures are caught and surfaced as a stage error by the existing CLI exception handler; a single local build crash is recoverable by the operator. Not a security-relevant DoS for a non-networked tool. |
</threat_model>
