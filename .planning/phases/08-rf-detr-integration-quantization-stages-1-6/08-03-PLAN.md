<objective>
Verify and lock in TensorRT standard-precision optimization (Stages 3-4) for
RF-DETR-Large: TF32, FP16, and BF16 engines built under the strict 2 GB workspace
limit.

The CLI orchestration for stages `3_trt_tf32`, `4_trt_fp16`, and `4_trt_bf16`
already exists in `cli.py._run_stage` and already routes through
`TensorRTEngine`. Phase 7 Plan 07-01 already keyed engine filenames by
`model_token` (sanitized `self.model_name` — `rfdetr-l` becomes `rfdetr_l` in
filenames, no collision with RT-DETR or YOLO engines). Plan 08-01 wired
`_get_adapter("rfdetr-l")` to return an `RFDETRAdapter`. Plan 08-02 produced the
simplified ONNX at `weights/rfdetr-l/rfdetr_l_sim.onnx`.

This plan's job is therefore **verification-driven**: run the three TRT builds
+ benchmarks on the RTX 3070 and confirm the architecture-agnostic builder
handles the RF-DETR graph topology (DINOv2 windowed attention with GridSample,
LayerNormalization, TopK from the encoder's two-stage proposal step) under the
strict 2 GB workspace. **No net-new TRT builder code is expected** — per
RESEARCH.md § "TRT 10.x Build Considerations" the architecture-agnostic builder
has been validated on RT-DETR (v1.0) and the YOLO family (Phase 7); the same
flags apply unchanged.

**Per the locked decisions (Phase 7 carry-forward + RF-DETR-specific):**
- **C-01 (locked):** Batch size strictly 1; warm-up 50 / measure 1000.
- **C-02 (locked):** TRT workspace strictly 2 GB
  (`config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 2 << 30)`).
  Expected RF-DETR workspace usage: ~1.0-1.5 GB (RT-DETR R50vd at 640 used
  ~0.6-0.9 GB in v1.0; RF-DETR-L at 704 has more attention heads but a small
  4-decoder-layer DETR head; total layer count is modest at 918 simplified
  nodes). Some headroom remains, but the checkpoint EXPLICITLY verifies build
  completes under 2 GB and flags if it doesn't (no auto-raise — that would
  violate C-02).
- **C-03 (locked):** TF32 builder flag enabled only for Stage 3 — the
  PyTorch FP32 baseline (Plan 08-01) had `torch.backends.cuda.matmul.allow_tf32
  = False`; the TRT TF32 build uses `trt.BuilderFlag.TF32` to deliberately
  enable Ampere tensor cores at 32-bit precision.
- **C-04 (locked):** BF16 availability checked at build time via
  `builder.platform_has_tf32` (Ampere proxy — TRT 10.x has no dedicated BF16
  attribute), then `trt.BuilderFlag.BF16` set when supported. On the RTX 3070
  (Ampere sm_86, `platform_has_tf32 == True`) BF16 IS expected to build —
  the graceful-skip path (`_BF16UnsupportedError` -> `skipped_reason`) is a
  runtime safety net for non-Ampere hardware. A `skipped_reason` populated on
  the RTX 3070 is a DEFECT to investigate, NOT a pass.

**RF-DETR-specific transformer ops (verified by researcher to work natively in
TRT 10.x):**
- **`INormalizationLayer`** (51 layers from `LayerNormalization` ops): native
  support since TRT 8.6. No plugin needed.
- **`GridSample`** (4 nodes — DINOv2 windowed attention position embedding
  interpolation): native support since TRT 8.5, mode=bilinear,
  align_corners=False (the DINOv2 default). No plugin needed.
- **`TopK`** (1 node — encoder two-stage `enc_outputs` proposal step):
  native support in TRT 10.x. No special handling.
- **BF16 + GridSample + LayerNorm**: no transformer-specific blockers documented
  for Ampere sm_86; the standard `platform_has_tf32` proxy applies.

Purpose: Stages 3-4 are the standard-precision optimization baselines that Plan
08-04's Stage 5 (INT8) and Stage 6 (Mixed Precision) are measured against. They
are also the diploma's "TensorRT standard precision" results column.

Output: Built TF32/FP16/BF16 engines under `engines/rfdetr-l/`, Stage 3-4 rows
in `results/rfdetr-l/<run_id>/results.csv`, a strengthened TRT engine unit test
pinning the rfdetr-l build contract, and a checkpoint confirming the engines
run correctly and the workspace stays under 2 GB.
</objective>
