<objective>
Verify and lock in TensorRT standard-precision optimization (Stages 3-4) for the YOLO
family: TF32, FP16, and BF16 engines for YOLO11l and YOLO26l.

The CLI orchestration for stages `3_trt_tf32`, `4_trt_fp16`, and `4_trt_bf16` already
exists in `cli.py._run_stage` and already routes through `TensorRTEngine`. Plan 01 fixed
the engine-filename collision so YOLO engines no longer overwrite RT-DETR's. This plan's
job is therefore **verification-driven**: confirm the existing builder produces valid
engines for the YOLO graph topology (which differs from RT-DETR — CNN backbone, YOLO11's
DFL/C2PSA head, YOLO26's NMS-free `(1,300,6)` output), confirm BF16 is gated correctly
on the Ampere RTX 3070, and confirm per-stage metrics land in the unified results files.

No net-new engine code is expected (D-04: reuse the v1.0 builder unchanged). If the
existing builder fails on a YOLO graph, that is a real finding to surface — but the
default expectation per RESEARCH.md is that the architecture-agnostic builder handles it.

**BF16 expectation on this hardware:** the target GPU is an RTX 3070 (Ampere, sm_86), on
which `builder.platform_has_tf32` is True and `trt.BuilderFlag.BF16` is supported.
Therefore on this machine BF16 **is expected to build successfully** for both YOLO
models (ROADMAP criterion 2). The graceful-skip path in the engine code
(`_BF16UnsupportedError` → `skipped_reason`) is a runtime *safety net* for non-Ampere
hardware — it is NOT an acceptable outcome here. A populated `skipped_reason` on the
RTX 3070 is a **defect to investigate before approval**, not a pass.

Purpose: Stages 3-4 are the standard-precision baseline that Stage 5 (INT8) and Stage 6
(Mixed Precision) are measured against.
Output: Built TF32/FP16/BF16 engines for both YOLO models, Stage 3-4 rows in
results.csv/results.json, a strengthened TRT engine unit test, and a checkpoint
confirming the engines run correctly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ONNX file → TensorRT `OnnxParser` → serialized engine | The YOLO ONNX graph (produced in Plan 01) is parsed and compiled by the TRT builder; a malformed graph could crash the builder or yield an invalid engine. |
| Serialized `.engine` file → `deserialize_cuda_engine` | Cached `.engine` files are deserialized and executed on subsequent runs without re-validation. |
| CLI args (`--engine-dir`, `--limit`) → filesystem + resource usage | User-supplied engine directory and image limit drive disk writes and GPU memory pressure. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05 | Tampering | YOLO ONNX graph parsed by `trt.OnnxParser` | mitigate | The ONNX file is validated with `onnx.checker.check_model` in Plan 01's `export_yolo_to_onnx` before it ever reaches the TRT parser; `_build_engine` additionally checks `parser.parse()` and raises `RuntimeError` with the parser errors if the graph is rejected, so a bad graph fails loudly rather than producing a corrupt engine. |
| T-07-06 | Tampering | Cached `.engine` file deserialized by `deserialize_cuda_engine` | accept | Engine files are produced locally by this same tool on this same machine and stored in an operator-controlled `engine_dir` (`.resolve()`-d in cli.py). There is no untrusted-engine ingestion path; treating a locally-built engine as trusted is proportionate for a single-user academic benchmark (ASVS L1). |
| T-07-07 | Denial of Service | TRT build exceeding the 8 GB VRAM budget | mitigate | `config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 2 << 30)` strictly caps the build workspace at 2 GB (D-06), and `BaseEngine.reset_vram_tracking()` clears the CUDA cache between engine builds — preventing one stage's allocation from starving the next. The checkpoint explicitly verifies no OOM. |
</threat_model>
