<objective>
Verify and lock in Stage 5 — INT8 calibration with all three calibrators (MinMax,
Entropy, Percentile) — for YOLO11l and YOLO26l, make the calibration image set
explicitly shared and provably deterministic per D-08, and implement D-12's latency
tie-break for the per-model best-calibrator selection.

The CLI orchestration for `5_trt_int8_minmax / _entropy / _percentile` already exists in
`cli.py._run_stage` and routes through `TensorRTEngine(precision="int8", ...)` with the
existing `int8_calibrators.py` (MinMax / Entropy / Percentile, the last using
`IInt8LegacyCalibrator` with the dummy histogram-cache overrides — RESEARCH pitfall 3).
Plan 01 fixed the calibration-cache filename collision so YOLO calibration caches no
longer overwrite RT-DETR's.

**Gap 1 to close (D-08) — explicit shared calibration set:** the current CLI Stage 5
path builds `COCODataLoader(limit=500)` inline in two separate branches (stage 5 and
stage 6). D-07 confirms 500 images; D-08 requires the **same 500 images** across all
three calibrators and both YOLO models so the calibrator algorithm is the only variable.

**Verified fact:** `COCODataLoader` is *already fully deterministic*.
`src/benchmark/data/coco_loader.py:162` does `self._image_ids = sorted(self._coco.getImgIds())`
then `[: self.limit]` — a stable sort of a fixed dataset followed by a fixed slice.
There is **no shuffle and no seed parameter**, and `load_calibration_data` iterates the
dataloader in that order, so `COCODataLoader(limit=500)` returns the identical 500
`image_id`s in the identical order on every construction. D-08 is therefore satisfied
*by construction* — the only gap is that the construction is duplicated inline, which
makes the "same 500 for stage 5 and stage 6" guarantee implicit rather than provable.
This task makes it **explicit and pinned**: factor the construction into one shared
helper used by both stages, and add a determinism test. **`COCODataLoader` itself must
NOT change** — adding a `seed`/shuffle parameter to it would be a regression (see the
explicit constraint in Task 1).

**Gap 2 to close (D-12) — latency tie-break:** D-12 says the per-model best calibrator
is "selected by highest mAP, **tie-broken by latency**". `logger.py:215`
`save_int8_best_calibrator` currently does `max(candidates, key=lambda x: float(x["map_50_95"]))`
— a pure mAP argmax with no tie-break. D-12 is a locked decision, so this plan adds the
tie-break: when two calibrators have equal `map_50_95`, the one with the lower
`latency_total_ms` wins.

The rest is verification: confirm the three calibrators complete for both YOLO graphs,
confirm `int8_best_calibrator.json` is written, confirm Stage 5 metrics land in the
unified results files. Per RESEARCH.md, YOLO11l pure-INT8 mAP drop may exceed 5% (DFL +
C2PSA sensitivity) and YOLO26l <0.5% — large pure-INT8 drops are expected findings, NOT
failures (D-14). This plan does not gate on accuracy; Plan 04 applies the D-14 gate.

Purpose: Stage 5 produces the three INT8 data points per model and selects the
per-model best calibrator that Stage 6 (Plan 04) builds on.
Output: INT8 engines + calibration caches for both YOLO models × three calibrators,
`int8_best_calibrator.json` per model (D-12 latency-tie-broken), Stage 5 rows in
results.csv/results.json, a calibration-determinism unit test, a tie-break unit test,
and a checkpoint confirming the runs.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| COCO val2017 images → calibration tensors → TensorRT calibrator | 500 operator-provided images are preprocessed into GPU tensors and fed to the TRT INT8 calibrator. |
| Calibration cache file → TensorRT builder | The `.cache` calibration table is read back on subsequent builds and trusted as calibration input. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-08 | Tampering | INT8 calibration `.cache` file reused across builds | accept | The calibration cache is produced locally by this tool and stored in the operator-controlled, `.resolve()`-d `engine_dir`.
